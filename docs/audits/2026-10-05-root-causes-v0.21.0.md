# Root causes behind the round-nine defects — rmap v0.21.0 (2026-10-05)

Companion to `docs/audits/2026-10-05-per-command-usefulness-v0.21.0.md`. Rule (human, 2026-09-06): an audit's defect list is not a fix queue; every defect gets a code-level cause before a packet is written. RC-1 was seam-read from source and reproduced live by the operator. RC-3 and RC-5 were checked by the operator against real output and the checkout. The other causes are grader-observed with the cited mechanism; each gets a seam read before its packet. Source citations hold for the release `751aeda9`: between `751aeda9` and `bea60edf`, only `docs/ROADMAP.md` changed.

## RC-1 (SEAM-READ + LIVE PROOF) — the repo root is stored relative to the database file; moving or copying a state root to another directory depth breaks every filesystem-backed surface, and orient states a false absence → STATE-ROOT-RELATIVE-REPO-ROOT-1

- Symptom (live, 2026-10-05, installed rmap 0.21.0 over stdio): the leveldb store from the witness root (`~/repo-graph-retained/audit-v0.21.0/databases`, 5 levels deep) copied unchanged to a root 8 levels deep. Same binary, same store bytes, same checkout:
  - `docs list` → exit 2 `repo root does not exist: /private/tmp/audit21-depth/a/b/c/root/databases/../../../../../Users/apple/Documents/APLICATII BIJUTERIE/legacy-codebases/leveldb`
  - `churn`, `hotspots`, `risk` → exit 2 `git churn failed: failed to spawn git: No such file or directory (os error 2)` — git is installed; the missing thing is the working directory, and the message names the wrong cause.
  - `check --full` → `PASS@Fresh` becomes `INCOMPLETE@Fresh`, `INDEX_DRIFT: … working-tree drift unknown (git could not be probed …) — run rmap refresh`.
  - `orient --budget medium` → exit 0, but `Docs: README.md, CONTRIBUTING.md.` disappears and the module section says `No README or architecture doc found — the tree is the best orientation.` leveldb has `README.md` and `CONTRIBUTING.md` at its root. This is a confident false absence, and it breaks RG-REQ-008-L07 ("a read failure renders a named unavailable reason"). The serving line drops `filesystem` from its sources without saying why.
  - `map --dry-run` → unchanged (`handlers/map.rs:33` canonicalizes with `unwrap_or(resolved)`; it plans the same files, whose content comes from the store).
  - Field instance: vscode re-indexed on the witness root (3 levels up from `databases/` to the shared `/Users/apple` prefix) and served from a copy at `/private/tmp/audit21-serve/root`: the same failures (captures `relocated-root-vscode-*.txt`). Captures: `relocated-depth-leveldb-*.txt`.
- Data path: at index time `daemon-runtime/src/util/context.rs:21 compute_storage_root_path` stores `pathdiff::diff_paths(canonical repo, canonical db dir)` in `repos.root_path`, and `repo-index/src/compose.rs:4619` rewrites it on every index. pathdiff climbs only to the COMMON PREFIX of the two paths, so the number of `..` steps encodes where the db directory sat when the repo was last indexed. At query time, eight sites join that string back onto the CURRENT db directory: `dispatch.rs:3512` (refresh), `:5751` (docs list), `:5881` (docs extract), `:4294` (query drift, via `handlers/quality/support.rs:19 resolve_root_path`), `handlers/quality/{churn.rs:100, hotspots.rs:110, risk.rs:99, coverage.rs:130}`, `handlers/map.rs:33`, and in storage `db_root_path.rs:43` (used by `agent_orient_reads.rs:65` doc inventory and `enrichment_impl.rs:822` enrichment root). `dispatch.rs:5797/:5972` also send the raw relative string to clients as `repo_path`. Basis for the site list: text search of `rust/crates` for joins of `root_path` and calls of the four resolvers, then a classification of all 37 non-test `.root_path` reads. This is a text search, not a compiler query; the fix slice should confirm the list by changing the stored type.
- Two sources of truth: the daemon registry already holds the absolute repo path (`registry.json` `canonical_path`, used to route every request and to index), and the store holds a second, relative copy. Nothing compares them, so they diverge silently after a move. Indexing keeps working because it uses the registry path, and `rmap index` heals the row, which is why the defect stays hidden.
- Why it never surfaced: the convention dates from the daemon extraction (3f9e584d 2026-05-07, a201c1a8 2026-05-12). Its stated purpose (`context.rs:7-10`: "DB and repo can be moved together") fits the old model, where `repo.db` sat next to the repo. Under the daemon model the databases sit in the state root, far from the repos, and what users move is the state root. Every audit since then has relocated its retained root from `/private/tmp/repo-graph-tests/<task>/databases` to `~/repo-graph-retained/<task>/databases`. Both paths are 5 levels deep, so the relative paths kept resolving by coincidence. Never worked (no regression).
- Who is hit: anyone who moves or copies a state root (a backup restore, renaming the home folder's state directory, the operator's retained-root copies), with any repo that shares a path prefix with the state root. Every repo under the home folder qualifies.
- Requirements: RG-REQ-008-L07 (named unavailable reason, broken by the false "No README"); RG-REQ-011-L06 (a run is fully defined by its state root); the honesty rule (unknown is never rendered as absent or as a different cause).
- Smallest fix (for the slice spec; decision-class items are marked): (1) The daemon resolves a repo's root from ONE source, the registry `canonical_path` it already holds at each handler's entry. One helper replaces the eight joins; the storage-layer readers (doc inventory, enrichment root) take the root as a parameter instead of re-deriving it. DECISION: keep `repos.root_path` for compatibility or stop writing it (it is the store's only record of its repo outside the registry). (2) When the root directory does not exist, every surface says so by name: `repo root not found: <path>` in place of `failed to spawn git`; orient and modules render the L07 unavailable reason, never "No README"; check names the missing root in INDEX_DRIFT. (3) `docs list` JSON `repo_path` carries the absolute root.
- Verification: a test that copies a store to a root at a different depth and asserts, on the live surfaces, that docs list, churn, hotspots, risk, coverage, check, orient's Docs line and refresh match the original-depth answers. Plus a test with the repo directory removed, asserting the named reason on each surface. Field re-run: this leveldb proof.

## RC-2 (GRADER-OBSERVED, OPERATOR-CONFIRMED) — Java `deps list` reports `0 import sites` on every row → DEPS-JAVA-IMPORT-SITES-1
- Symptom: kafka `deps list clients` row `com.github.luben.zstd (0 import sites, 2 call sites)`. Ground truth: `clients/src/main/java/org/apache/kafka/common/compress/ZstdCompression.java:27-30` holds four `import com.github.luben.zstd.…` statements. 8 of 9 Java rows in the supplementals read `0 import sites`. The judge shows that grpc-java example-tls's 6 helloworld import statements appear as `6 call sites`, and that the store holds perfmark IMPORTS rows that the row reports as 0.
- Mechanism (to seam-read): the Java dependency reducer files import evidence under the call-site predicate, or never reads the IMPORTS rows for Java. The adjudicator notes that a row with 10 imports and 9 "call sites" means the relabelling is not exact. The cause must be read before the packet.
- Requirements: RG-REQ-002-L03/L04 (a count names its predicate); RC-8 of round eight (absorbed by DEPS-GRADLE-CATALOG-1B), which stays PARTIAL.
- Same surface: same-module and JDK packages read `undeclared` (kafka clients `org.apache.kafka.common.header`, `javax.management`; grpc core `io.grpc`); the header `Java dependency attribution unavailable` prints above attributed Gradle rows. Follow-ups DEPS-JAVA-SELF-1 and DEPS-JDK-BUILTINS-1.

## RC-3 (OPERATOR-VERIFIED) — trust's `Edges: 100% resolved (N of N)` is a tautology → TRUST-EDGES-TAUTOLOGY-1
- Symptom: all 25 smoke trust captures print `Edges: 100% resolved (N of N)` (leveldb `4187 of 4187`), next to thousands of unresolved imports and calls on the same screen.
- Mechanism: stored edges are resolved by construction, because unresolved references live in `unresolved_edges` (`storage/src/migrations/migration_007.rs:14`). So the ratio is resolved ÷ resolved. The line states a measurement that cannot vary.
- Smallest fix (for the spec): drop the line, or make the denominator include `unresolved_edges` and name the predicate.

## RC-4 (GRADER-OBSERVED) — Rust intra-crate directory nesting reads as "module-level cycles" and triggers trust's registry/factory downgrade → CYCLES-RUST-POPULATION-1 (filed) + a trust-heuristic guard
- Symptom: repo-graph `cycles` prints `9 module-level cycles found` (1 last round); eight are parent↔child directories inside one crate (`rust/crates/agent/src -> rust/crates/agent/src/explain -> rust/crates/agent/src`). trust prints `Change-impact: LOW (alias resolution suspected; registry/factory patterns detected)` with `registry_pattern_suspicion: ancestor_with_5_parent_child_cycles:…`.
- Cause: RUST-SELF-RESOLUTION-1 binds `use crate::…`/`super::…` correctly, and that exposes the `mod x;` ↔ `use crate::x` shape as directory-group cycles. This was predicted and accepted (D-RSR-DIR-CYCLES-1). In the field, the header still says "module-level", and a trust heuristic written for registry/factory patterns now fires on idiomatic Rust.

## RC-5 (OPERATOR-VERIFIED) — `explain <type>` `Referenced by (N files)` counts direct includers of the defining file, without saying so → EXPLAIN-REFERENCED-BY-PREDICATE-1
- Symptom: leveldb `explain Slice` → `Referenced by (20 files)`. Ground truth: 20 files `#include` `slice.h` directly (grep over `*.cc`/`*.h`); 89 files contain the token `Slice`. The adjudicator: 89 textual mentions do not prove 89 semantic users. The defect is the unstated predicate, not a specific count.

## RC-6 (GRADER-OBSERVED; operator-confirmed mechanism) — batch-index client timeouts
- Symptom: gstreamer, hadoop, kafka and vscode printed `index … is STILL RUNNING on the daemon — the client's 300s read timed out, the operation did not … follow it with rmap doctor` (exit 3, documented). The smoke treated that as a failure and moved on, so up to four indexes ran at once on one daemon. hadoop finished detached after about 1 h 42 m. vscode's index was cut by the smoke's daemon shutdown and finished in 992 s when run alone over stdio.
- Mechanism: `rgr/src/daemon_client/connection.rs:38 READ_TIMEOUT_SECS = 300` is a per-read timeout, so it fires after 300 s of silence in a phase. The documented override is `RMAP_LONG_OP_READ_TIMEOUT_SECS` (`rgr/src/commands/index.rs:30`; RG-REQ-011 frozen list). Round eight had no index timeouts.
- Not established: whether the daemon caps concurrent indexes (a text search is not proof of absence), or whether a solo socket phase can stay silent for 300 s. The client note is honest and actionable. The harness contributes (next RC).

## RC-7 (OPERATOR) — harness: an index failure breaks the F6 accounting
- `scripts/smoke-validation-repos.sh:410 FAILED_REPOS+=("$REPO_NAME:index")`; the F6 set comparison (`:618-630`) matches bare repo names, so every index failure also reports `repo accounting mismatch`. The `--retain` misplacement in this round's launch (operator error) marked all 29 repos failed. Harness fix: record the bare name and keep the reason elsewhere; reject an unknown `--flag` in the command list.

## RC-8 (OPERATOR) — record defect: `docs/ROADMAP.md:1415` quotes `--direction outbound`
- The binary accepts only `--outbound`/`--inbound` (`rgr/src/commands/modules/deps.rs:184-185`); the slice spec recorded the correction (`docs/slices/modules-deps-summary-scope-1.md:432`). Corrected by a dated ROADMAP entry (append-only).
