## 1. Problem (verified at HEAD 6cbf012f)

Every full index and every refresh writes a snapshot toolchain stamp, and nothing ever reads it back. The stamp names the toolchain of the write that created the snapshot; after a refresh it does not assert that this toolchain produced every copied-forward fact (RG-REQ-001-L06), so this slice treats it as a stamp to compare, never as a record of which rmap produced the facts served. `build_toolchain_json` (`rust/crates/indexer/src/orchestrator.rs:1457-1464`) writes `{"extractors":[names],"indexer":INDEXER_VERSION}` into the snapshot row of every full index (`:250`) and every refresh (`:1812`); `INDEXER_VERSION` is `:59` and a literal copy sits at `rust/crates/repo-index/src/compose.rs:1653`. The extractor names come from six constants (`ts-extractor/src/extractor.rs:20` `ts-core:0.2.0`, `c-extractor/src/extractor.rs:21` `c-core:0.1.0`, `cpp-extractor/src/extractor.rs:26` `cpp-core:0.1.0`, `java-extractor/src/extractor.rs:24` `java-core:0.1.0`, `python-extractor/src/extractor.rs:18` `python-core:0.1.0`, `rust-extractor/src/extractor.rs:20` `rust-core:0.2.0`), composed into the extractor list twice — the index path (`compose.rs:3361-3403`) and the refresh path (`compose.rs:3854-3895`). The only reader of `toolchain_json` in the daemon is the trust pass-through (`daemon-runtime/src/util/trust.rs:44`); no `orient` or `check` path compares it with the running binary. A refresh copies unchanged files' facts forward and toolchain versions are not an invalidation input (D-REFRESH-STALE-1), so when an extractor or resolver slice changes what the index produces, every existing store keeps the old facts silently until someone runs `rmap repo rebuild`.

Code under analysis (the witness the packet names; EXECUTED 2026-09-26, python `sqlite3` with `?immutable=1` on the retained store, never served): the leveldb v0.19.0 store `~/repo-graph-retained/audit-v0.19.0/databases/1196d1380537d43e.db` holds one snapshot, `full`/`ready`, created `2026-09-22T23:02:04.969Z`, basis `7ee830d02b623e8ffe0b95d59a74db1e58da04c5` (= the leveldb checkout's HEAD), stamped:

```
{"extractors":["ts-core:0.2.0","c-core:0.1.0","cpp-core:0.1.0","java-core:0.1.0","python-core:0.1.0","rust-core:0.2.0"],"indexer":"indexer:1.0.0"}
```

The v0.18.0 leveldb witness store carries the same bytes. That is exactly the running toolchain at HEAD: no version constant has moved since v0.18.0. Consequence for this slice's proof: an unmodified copy of the witness is **current** — it must start nothing and render nothing (the P-TS-02 witness) — and the stale path is proven on a copy whose stamp is rewritten in the copy (never in the retained store) to a recorded differing value, `cpp-core:0.0.0` (§2.3).

## 3. Regression watch

- Existing daemon/rgr tests whose READY fixture snapshot carries a NULL stamp and that go through `handle_orient`/`handle_check` would now see the additive `toolchain_staleness` key (state `unknown`) and a line. At HEAD, the daemon-runtime fixtures that write NULL stamps and serve `orient`/`check` build their envelopes below the post-serialize attach (e.g. `orient_lg_decisions/served_e2e.rs` calls the envelope builders), and the integration fixtures that write NULL stamps write `building` snapshots only (`daemon_crash_recovery.rs:104-117`, `daemon_visibility.rs:702-716`), so none is expected to move — the suites decide (§4).
- The first-use hook runs inside `load_repo` for every request type; it enqueues in memory only and reads nothing, so no read path gains latency. The worker's stamp read at job start is one gated single-row read.
- The automatic index is an ordinary `index`: it chains enrichment → seed → retention like any index (retention then prunes the previous snapshot when enabled), it holds the write lock while it runs (an explicit `rmap index`/`refresh`/`rebuild` of that repository arriving meanwhile waits or bounces exactly as it does behind another client's index today), and a daemon crash mid-run leaves a `building` snapshot the existing reconciliation marks interrupted; the next process's first use queues the check again.
- A race is inherent and harmless: a request that pinned the old snapshot while the job completed reports `re-index queued` (LD-07) and its queued check finds the new snapshot current and starts nothing.
- **Known limitation — user-supplied include roots (D-TS-RUNTIME-1 §2).** The automatic re-index is a flagless full index: it resolves C/C++ includes with the derived roots only (CPP-INCLUDE-ROOTS-1), so a repository last written with `--include-root` loses those roots' resolutions at its automatic re-index. This is the same behaviour a plain `rmap refresh` without the flag has today — user roots are read only from each request's parameters and persisted nowhere (`dispatch.rs:3097-3108`; `rgr/src/commands/index.rs:1356-1407`; `orchestrator.rs:290`, `:1997`) — so the slice introduces no new loss class; the remedy is to re-run `rmap index`/`refresh` with the flag. Persisting the effective include roots for every write path (refresh, index and the automatic re-index) is follow-up INCLUDE-ROOTS-PERSIST-1 (§8), one data-shape change for all three.
- **Stamp, not provenance.** The status compares the snapshot toolchain stamp only; after a refresh the stamp names the refreshing toolchain and does not assert that it produced every copied-forward fact (L06). A store refreshed by the running binary therefore reports `current` even when copied-forward facts came from an older extractor — accepted by D-STALE-SIGNAL-1 (a stale index is a signal, not a tracked property) and stated here so no surface or reviewer reads producer provenance into the line.
