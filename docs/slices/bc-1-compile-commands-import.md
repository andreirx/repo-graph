# BC-1: Build Context Import (compile_commands.json)

Status: PLANNED
Depends: TC-1 (toolchain inventory)
Unblocks: Native semantic enrichment, include path resolution, define-aware extraction
Track: Toolchain-Aware Evidence Import
Layer: 1 (architectural substrate — build context provenance)

## Goal

Import `compile_commands.json` as build context provenance, enabling downstream
native semantic improvements and providing translation unit boundaries as
first-class facts.

**Rationale:** For C/C++ repos, `compile_commands.json` is the most important
local artifact. It contains:
- Include paths (-I flags)
- Defines (-D flags)
- Language mode (-std=)
- Translation unit boundaries
- Compiler used per file

Without this, native extraction stays syntax-only. With it, we can:
- Resolve includes accurately
- Know which defines affect which files
- Provide context to clangd for semantic enrichment
- Understand generated source visibility

## Problem Analysis

### Current State

- C/C++ extraction is tree-sitter syntax-only
- No include path information
- No define information
- No translation unit boundaries
- Cannot feed compile context to clangd

### What compile_commands.json Provides

```json
[
  {
    "directory": "/path/to/build",
    "command": "clang -I/usr/include -I./include -DDEBUG=1 -std=c11 -c file.c -o file.o",
    "file": "/path/to/repo/src/file.c",
    "output": "/path/to/build/file.o"
  },
  ...
]
```

Extractable information per translation unit:
- `file`: source file path
- `directory`: working directory for relative paths
- `command` or `arguments`: full compiler invocation
- Include paths: `-I<path>`, `-isystem<path>`
- Defines: `-D<name>`, `-D<name>=<value>`
- Language mode: `-std=c11`, `-std=c++17`
- Compiler: first token of command

### Generation Sources

`compile_commands.json` can be generated by:
- CMake: `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`
- Bear: `bear -- make`
- Ninja: built-in support
- compile-db: various build system wrappers
- Bazel: via aspects or external tools

## Scope

### In Scope

1. **compile_commands.json parser**
   - Parse standard JSON compilation database format
   - Extract per-file compile commands
   - Parse command/arguments into structured flags

2. **Build context model**
   - `TranslationUnit`: file + include paths + defines + language mode + compiler
   - `BuildContext`: collection of translation units + generation metadata

3. **Snapshot provenance integration**
   - Store build context as snapshot provenance
   - Record compile_commands.json location and mtime
   - Enable comparability checks

4. **CLI surface**
   - `rmap build-context import <db> <repo> <compile_commands.json>`
   - `rmap build-context show <db> <repo> <file>` — show compile context for a file
   - `rmap build-context list <db> <repo>` — list translation units

5. **Include path extraction**
   - Extract `-I` and `-isystem` paths
   - Normalize to absolute paths
   - Store per translation unit

6. **Define extraction**
   - Extract `-D` flags
   - Parse name and optional value
   - Store per translation unit

### Out of Scope (Later Slices)

- Actually resolving includes (requires file reading)
- Feeding context to clangd (that's semantic enrichment slice)
- Generating compile_commands.json (user generates, imports result)
- CMake integration beyond reading the output file

## Design

### Data Model

```rust
pub struct BuildContext {
    pub source_path: PathBuf,      // Path to compile_commands.json
    pub source_mtime: String,       // ISO8601
    pub generated_by: Option<String>, // "cmake", "bear", etc. if detectable
    pub translation_units: Vec<TranslationUnit>,
}

pub struct TranslationUnit {
    pub file: String,               // Repo-relative source file path
    pub compiler: String,           // "clang", "gcc", etc.
    pub language_mode: Option<String>, // "c11", "c++17", etc.
    pub include_paths: Vec<IncludePath>,
    pub defines: Vec<Define>,
    pub output: Option<String>,     // Object file path
}

pub struct IncludePath {
    pub path: PathBuf,              // Absolute or repo-relative
    pub kind: IncludeKind,          // User (-I) or System (-isystem)
}

pub enum IncludeKind {
    User,
    System,
}

pub struct Define {
    pub name: String,
    pub value: Option<String>,
}
```

### Parser

```rust
pub fn parse_compile_commands(json: &str) -> Result<Vec<RawCompileCommand>, BuildContextError> {
    // Standard format: array of objects with directory, command/arguments, file
    let commands: Vec<RawCompileCommand> = serde_json::from_str(json)?;
    Ok(commands)
}

pub fn extract_translation_unit(
    cmd: &RawCompileCommand,
    repo_root: &Path,
) -> Result<TranslationUnit, BuildContextError> {
    let args = parse_command_line(&cmd.command_or_arguments())?;
    
    let compiler = args.first().map(|s| extract_compiler_name(s));
    let include_paths = extract_include_paths(&args, &cmd.directory);
    let defines = extract_defines(&args);
    let language_mode = extract_language_mode(&args);
    let file = normalize_path(&cmd.file, repo_root)?;
    
    Ok(TranslationUnit {
        file,
        compiler: compiler.unwrap_or_default(),
        language_mode,
        include_paths,
        defines,
        output: cmd.output.clone(),
    })
}

fn extract_include_paths(args: &[String], directory: &Path) -> Vec<IncludePath> {
    let mut paths = Vec::new();
    let mut iter = args.iter().peekable();
    
    while let Some(arg) = iter.next() {
        if arg.starts_with("-I") {
            let path = if arg.len() > 2 {
                &arg[2..]
            } else {
                iter.next().map(|s| s.as_str()).unwrap_or("")
            };
            paths.push(IncludePath {
                path: resolve_path(path, directory),
                kind: IncludeKind::User,
            });
        } else if arg.starts_with("-isystem") {
            // Similar handling for -isystem
        }
    }
    
    paths
}
```

### Persistence

**Option A: JSON blob in snapshots**
- Add `build_context_json TEXT` to snapshots
- Simple, self-contained
- Limited queryability

**Option B: Normalized tables**
```sql
CREATE TABLE translation_units (
    snapshot_uid TEXT,
    file_path TEXT,
    compiler TEXT,
    language_mode TEXT,
    include_paths_json TEXT,  -- Array of paths
    defines_json TEXT,        -- Array of {name, value}
    PRIMARY KEY (snapshot_uid, file_path)
);
```

**Recommendation:** Option B. Translation units are queryable per-file, which
matters for "what compile context applies to this file?" queries.

### CLI

```bash
# Import compile_commands.json
rmap build-context import ./repo.db repo-uid ./build/compile_commands.json

# Show compile context for a specific file
rmap build-context show ./repo.db repo-uid src/main.c
# Output: compiler, include paths, defines, language mode

# List all translation units
rmap build-context list ./repo.db repo-uid

# Check if build context exists
rmap build-context status ./repo.db repo-uid
```

## Dependencies

- Snapshot provenance infrastructure (EXISTS)
- `serde_json` for parsing
- `shlex` or equivalent for command line parsing

## Risks

- Command line parsing is complex (quoting, escaping)
- compile_commands.json format has minor variations
- Large projects may have thousands of translation units

Mitigation:
- Use robust command line parser (shlex crate)
- Handle both `command` and `arguments` fields
- Efficient storage with normalized table
