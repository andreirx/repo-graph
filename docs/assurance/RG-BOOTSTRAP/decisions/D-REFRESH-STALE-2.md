# D-REFRESH-STALE-2 — Where does the provenance of copied-forward facts live, so a refresh cannot launder toolchain staleness?

Raised: 2026-09-23 by the third independent review of RG-BOOTSTRAP-INPUT-9 (codex gpt-6-sol), verified on the source: a refresh creates its snapshot stamped with the RUNNING toolchain (`indexer/src/orchestrator.rs:1812-1821`, `build_toolchain_json(extractors)` → `create_snapshot(kind: Refresh, toolchain_json: Some(...))`) and then copies every unchanged file's facts forward (`copy_forward_unchanged_files`). A snapshot-level comparison of that stamp with the running binary — what D-REFRESH-STALE-1's option B first prescribed — reports `current` after the first refresh by a newer binary although every unchanged file's facts were produced by the older extractor: the refresh that cannot fix the facts would erase the warning about them. Staleness must follow the provenance of the facts SERVED; how that provenance is persisted is a data-shape choice across the store boundary.
Resolved: 2026-09-23 by the HUMAN — option B.

## Options
- **A** — per-file extractor version: each file row records the extractor version that produced its facts, copy-forward carries it, the comparison groups served files by family. Reward: exact — the line can name which families (even which files) are stale, and a store becomes current once every file has been re-extracted, without a rebuild. Risk: a schema migration plus changes on the extraction write path and the copy-forward path; the largest of the three; a per-request GROUP BY on orient/check.
- **B (ratified)** — carried-forward provenance inside the snapshot stamp: the refresh snapshot's `toolchain_json` keeps `extractors`/`indexer` = running (honest about what extracted the changed files, as RG-REQ-001-L09 wants) and gains `carried_forward` whenever files are copied; for each extractor family represented by copied files it retains the union of that family's parent stamped and carried-forward versions, and it retains the corresponding indexer versions whenever any file is copied; the comparison evaluates an extractor family only when the served snapshot contains files of that family and flags an evaluated family when the running version differs from its snapshot stamp or any retained version for that family; the indexer is evaluated always. (Value-shape amendment by the OPERATOR after review pass 4 of INPUT-9, 2026-09-23: the first draft carried a single version per family — "the parent's carried-forward where present, else its stamp" — which loses the parent's stamped version after a second refresh (index under A, refresh under B, refresh under A copies B's facts and reports current). The set is option B's own principle applied faithfully; the human may override.) Reward: no migration or per-file provenance field; the comparison remains a pure function of snapshot toolchain provenance, running versions, and extractor-family names represented by served files; `trust`, which already reads `toolchain_json` (`daemon-runtime/src/util/trust.rs:44`), keeps working because the existing keys are unchanged. Risk: coarse — one copied-forward C++ file keeps the whole C++ family stale until a rebuild; acceptable because the ratified remedy is the rebuild, not an incremental cure.
- **C** — the refresh snapshot inherits the parent's stamp; only a full index writes the running toolchain. Reward: no data-shape change at all; the original snapshot-level comparison works unchanged. Risk: the stamp then misdescribes the changed files (extracted by the new binary) — weakens L09's provenance intent and shows the old version on `trust`.

## Resolution
RG-REQ-001-L06 amended (INPUT-9) with the per-family `carried_forward` set, the differs-from-stamp-or-any-retained rule, the lowest differing semantic version as `snapshot_version`, and the one-refresh, two-refresh (A → B → A), deleted-family and malformed-provenance verification cases; D-REFRESH-STALE-1's responsibility split corrected. TOOLCHAIN-STALENESS-1 implements both.
