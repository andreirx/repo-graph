# D-PRB-ENRICH-1 — How PYTHON-RECEIVER-BINDING-1's certainty rule accounts for the compiler-promotion path

Raised: 2026-09-24 by the second document review of PYTHON-RECEIVER-BINDING-1 (reviewer codex gpt-6-sol, decision D-PRB-ENRICH, findings F-PRB-ENRICH-WRITE and F-PRB-ENRICH-READ): the enrichment promoter writes CALLS edges with `resolution = 'inferred'` and the storage layer counts them into the persisted certain-call aggregate — a path the slice's D-PRB-RATE-1 = A rule ("the numerator counts `static`/`dynamic` only") would silently contradict.
Resolved: 2026-09-24 by the OPERATOR — option A below, an implication of RG-REQ-005-L02 as ratified. The human may override.

## The mechanism (verified on the source and on the v0.19.0 witness stores)
- `enrichment/src/promotion.rs:173-350` (`promote_edges`, eight gates): an unresolved `obj.method()` call is promoted ONLY when the compiler (rust-analyzer, jdtls, tsserver) resolved the receiver's type (gate 3, `ReceiverTypeOrigin::Compiler`), the type is internal (gate 4), it maps to exactly one CLASS (gate 5) and the method to exactly one METHOD on it (gate 6). The written row: `edge_type = CALLS`, `resolution = RESOLUTION_INFERRED` (`:47`, the literal `"inferred"`), `extractor = "compiler-promotion:0.1.0"` (`:41`), `metadata_json = {promotedFrom, receiverType, methodName}` (`:344-348`). IMPORTS are never promoted (no `IMPORTS` literal in the crate).
- `storage/src/enrichment_impl.rs:598-700`: each landed CALLS row is pushed to `inserted_call_endpoints`; `crud::snapshots::adjust_resolved_call_aggregate` (`:698`) adds the count to `snapshots.resolved_call_count` and `adjust_resolved_call_file_pairs` (`:788`) updates the per-file-pair census — the promoted edge is COUNTED AS RESOLVED today. The live fallback `query_call_resolution_total` (`storage/src/call_resolution_reads.rs:205-208`) counts every CALLS row regardless of resolution.
- Scale: on `~/repo-graph-retained/audit-v0.19.0` (immutable read), 439 CALLS rows carry `resolution='inferred'`, all `compiler-promotion:0.1.0`, in four stores (380 / 43 / 9 / 7). No before-root of this run holds any (enrichment off).

## The contradiction
RG-REQ-005-L02: a call binds as `static` "when receiver-type evidence selects one" candidate; a binding "on a bare name alone with an UNTYPED receiver" is INFERRED. A compiler-resolved receiver type that selects exactly one class and one method IS receiver-type evidence selecting one — by the catalog the promoted binding is `static`. The `Resolution` doc (`indexer/src/types.rs`: Inferred = "guessed from naming, proximity, or heuristics") says the same. The promoter's label `inferred` is a name that does not match its semantics: the row carries proof, and the aggregate already treats it as certain. RG-REQ-002-L11 ("never counts [an inferred fact] among certain facts") then leaves two consistent readings only: relabel the promoted row to what its evidence earns, or stop counting it.

## Options
- **A (ratified by the operator)** — the promoter writes `resolution = 'static'` for the rows it proves (`promotion.rs:47` and the assertion at `:496`), `PROMOTER_VERSION` → `compiler-promotion:0.2.0`, metadata unchanged (`promotedFrom`, `receiverType`, `methodName` keep the provenance; `extractor` names the promoter). The aggregate adjustments at `enrichment_impl.rs:698/:788` stay correct with no exception clause; PRB1's readers partition by `resolution` alone. Legacy stores (the 439 witness rows) keep `inferred` until re-enrichment: PRB1's inferred readers treat an inferred CALLS row WITHOUT a `basis` as present-malformed for the name-only contract and render its reason from the extractor family ("inferred: compiler-promotion (label predates 0.2.0 — re-enrich)"), one test per evidence state (absent / present-valid / present-malformed). Reward: one rule — `resolution` states the evidence class, every reader (trust, `dead`, `callers`, `path`, `explain`) applies the same predicate, enrichment keeps its purpose (raising the certain share with proof). Risk: a served field's value changes for promoted rows (truthful; the extractor still says who wrote it); `enrichment/src/promotion.rs` and its tests join the allocation (two literals, one version, one assertion); stale-label rows on old stores are excluded from certain facts until re-enriched — the toolchain-staleness surface (RG-REQ-001-L06) names the version gap.
- **B** — keep `inferred`; the numerator counts `static`/`dynamic` plus inferred rows whose extractor family is `compiler-promotion`. Reward: the promoter is untouched. Risk: `inferred` means two things (a proof and a guess) told apart by a side field — every partitioning reader carries a two-key predicate, and RG-REQ-002-L11's rule acquires an exception it does not state.
- **C** — keep `inferred` and stop counting promoted rows (drop the adjustment at `:698/:788`). Reward: the simplest predicate. Risk: enrichment no longer raises the certain share; a compiler-proven binding is rendered "investigate" — a certain fact presented as a guess, the inverse fabrication.
- **D** — a prerequisite slice settling the promoter first (the reviewer's option B). Reward: PRB1 stays bounded. Risk: the prerequisite is this decision; PRB1 (the audit's first-ranked class) waits one more item for a two-literal change.

## Resolution
A. PYTHON-RECEIVER-BINDING-1's allocation adds `rust/crates/enrichment/src/promotion.rs` (the resolution literal, `PROMOTER_VERSION` 0.2.0, the test at `:496`) and the enrichment storage tests that assert the written resolution; the read contract covers a legacy inferred row without `basis` (reason from the extractor family); the ship block reports the promoted-row count on any store it re-enriches. D-PRB-RATE-1 = A stands unchanged.
