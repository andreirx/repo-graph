# D-DAP-NESTED-BUILDS-1 — a Gradle build whose `settings.gradle` lies below the repository root is a build of its own: its root project and the projects its `include` lines name are Gradle-DECLARED modules; nothing under it attributes to the repository root

Raised: 2026-10-04 by the manager packeting round-eight queue item 7 (RC-9, `docs/audits/2026-10-03-root-causes-v0.20.0.md`; the 1A follow-up DGC-ATTRIBUTION-PRECISE-1).

**The problem in plain words.** `rmap deps list` on grpc-java prints the root row `.  [examples/android/clientcache/app/build.gradle (+19 nested java manifests, 38 declared across 20)]` / `used 35 · no static import found 3` — the EXAMPLE APPS' facts under the root's name (VERIFIED live 2026-10-04 on an isolated copy of the retained v0.20.0 store). grpc-java's `examples/` holds 20 separate Gradle builds, each with its own `settings.gradle` (108 Java files). Gradle module discovery reads ONLY the root `settings.gradle` (`repo-index/src/compose.rs:590` collects `rel_path == "settings.gradle"`; `:1116-1128 extract_gradle_modules`), so no nested build is a module; its files fall to the repository root by longest-prefix ownership (`compute_cargo_file_ownership`, root ranks last — D-DGC-BOUNDARY-1 (7)) and its manifests attach to the root row by longest-ancestor directory. MEASURED across the corpus: nested `settings.gradle` builds in grpc-java (20; the root has its own settings), gstreamer (3), rabbitmq-tutorials (3), vcmi (1) and hexmanos (1) — the last four have NO root settings, so today their Gradle projects are discovered nowhere (hexmanos's 74-file Java `backend/` is not a module). 1A already treats a nested settings file as its own BUILD for declared-set attribution (`gradle_nested_settings_file_defines_its_own_build`); the module model did not.

**Options presented to the human (reward / risk, by usefulness to an agent net of misdirection).**
- A — nested builds are declared modules: every `settings.gradle` / `settings.gradle.kts` in the repository (outside `node_modules`, build output and other excluded trees) defines a build; its root project (the settings file's directory) and the projects its `include` lines name (mapped through that file's `projectDir` relocations) become Gradle-declared module candidates, keyed by filesystem path (RG-REQ-004-L11: one identifier space — two nested roots both have Gradle path `:`, so the canonical path is the directory); the method line states the count of settings files (`N Gradle projects from K settings.gradle files`); `deps list`, `modules list`, `trust` and `cycles` each get the build's rows; the repository root keeps only its own files; nothing under a nested build attributes upward. Reward: the agent asking about `.` sees the root project's facts; asking about `examples/example-tls` or hexmanos's `backend` sees that build's row; four repositories gain their Gradle modules. Risk: the module universe grows on five corpus repos (grpc-java ≈ +24, gstreamer ≈ +10, rabbitmq-tutorials ≈ +3, vcmi ≈ +2, hexmanos +1) — every module surface re-measured, a full re-index; declared discovery under RG-REQ-004-L03, not inferred (L04's "no further discovery" untouched).
- B — boundary only: files and manifests under a nested settings file never attribute upward and the root row states `N files under K nested Gradle builds (not modules of this build)`; no new rows. Risk: the nested builds' own facts stay unavailable.
- C — label only. Risk: the root figures stay the examples' figures.
- D — defer.

Resolved: 2026-10-04 by the HUMAN: **"Nested builds are declared modules (Recommended)"** — option A.

## What this record rules
- Discovery: every settings file in the scanned tree defines a Gradle build; the build's root project is the settings file's directory; its `include`d projects resolve against that directory (and its `projectDir` relocations, as the root build's do today).
- Identity: a Gradle module's canonical path is its filesystem directory; the display name follows RG-REQ-004-L10's collision rule (two `app` projects are disambiguated by their manifest path).
- Attribution: declared sets, manifest records and file ownership follow the build the file belongs to (the nearest settings directory above it); the repository root's row carries only files no nested build owns.
- Method line (RG-REQ-004-L03, a wording CHANGE recorded in the slice's `changes`): `N Gradle projects from K settings.gradle files (M relocated via projectDir)` when K > 1; the single-file wording unchanged when K = 1.
- Nothing inferred changes: a nested build's directories are declared coverage, so inferred detection does not run inside them (the existing `collect_declared_module_roots` rule).

## Correction 2026-10-04 (operator; references "What this record rules — Attribution" above and the INPUT-1 document review's D-DAP-NON-JVM)
The sentence "nothing under a nested build attributes upward" and "the repository root's row carries only files no nested build owns" overreach: file ownership is PER TOOLCHAIN by ratified RG-REQ-004-L03 ("a logical package is defined per toolchain — Rust = nearest Cargo.toml crate; TS/JS = nearest package.json workspace package; JVM = …"), and `persist_gradle_modules` owns JVM files (`.java`, `.kt`, `.scala`) only. Corrected scope (the reviewer's option B): a nested Gradle build owns the JVM files under its project directories and its Gradle manifests; a non-JVM file beneath it (vcmi's or gstreamer's C/C++ JNI sources) keeps its own toolchain's ownership rule — the inferred directory group, as today — and the existing partition between toolchains is unchanged. What the human ruled stands in substance: nested builds are declared modules; their JVM files and manifests never attribute to the repository root. Option A (one ownership across toolchains under a Gradle directory) would change C/C++ directory-group ownership and every downstream module surface — a different decision, not taken here.
