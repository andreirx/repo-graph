# D-SRR-ROOTPATH-1 — human decision (2026-10-05): keep `repos.root_path` in the store, never read it to find the working tree

Raised: 2026-10-05 by the operator (in-place manager) while root-causing audit round nine's RC-1 (`docs/audits/2026-10-05-root-causes-v0.21.0.md`), before the slice STATE-ROOT-RELATIVE-REPO-ROOT-1 was specified.

**The problem in plain words.** Every repository store records its repository's root in `repos.root_path`, as a path RELATIVE to the store file's directory (`daemon-runtime/src/util/context.rs:21 compute_storage_root_path`, `pathdiff::diff_paths`; rewritten on every index at `repo-index/src/compose.rs:4619`). The daemon registry records the same repository's ABSOLUTE `canonical_path`, and that is the path every request is routed by and every index runs from. When a state root is moved or copied to a directory at a different depth, the relative path points at a directory that does not exist, and every surface that reads the working tree through it fails or, worse, reports an absence (`orient` prints `No README or architecture doc found` beside a real README; live proof on the v0.21.0 leveldb store). The fix makes the daemon resolve the root from the registry everywhere. The question is what happens to the stored relative field.

**Options presented (reward / risk).**
- A — keep the field, stop reading it for resolution. Reward: smallest change; no schema migration; old stores and older binaries keep working unchanged; the fix stays inside the daemon's resolution sites. Risk: a field nothing should read stays in the schema, and a future change could read it again and bring the defect back — mitigated by a test that fails if a working-tree resolver reads it, and a comment on the field.
- B — store absolute paths. Reward: the stored field becomes true and agrees with the registry; existing stores are rewritten on their next index. Risk: two copies of one fact remain; a store copied to another machine or home directory carries a wrong absolute path; older binaries interpret the field as relative.
- C — drop the field. Reward: one source of truth enforced by the schema. Risk: a schema migration on every store (a boundary change); the store no longer records its repository without the registry; the largest slice.

**Decision: A** — human, 2026-10-05 ("Keep it, stop reading it (Recommended)"). Consequences: (1) `compute_storage_root_path` and the index-time rewrite stay unchanged, so the stored bytes of every store stay unchanged; (2) no working-tree reader in the daemon or the storage crate resolves a path from `repos.root_path`; (3) a test fails if one does; (4) the field's doc comment states that it is retained for compatibility and is not a resolution source.

**Correction 1 (2026-10-05, operator; appended — the text above is not rewritten; the human's decision A is unchanged).** Consequence (1) above overstated "the stored bytes of every store stay unchanged". The first document review of STATE-ROOT-RELATIVE-REPO-ROOT-1 (codex gpt-6.1-sol, finding F-SRR-08) observed that refresh recomputes `repos.root_path` from the current store directory (`dispatch.rs:3557` via `compute_storage_root_path`), as index does (`repo-index/src/compose.rs:4619`). The decision's intent, restated: no migration and no eager rewrite of existing stores; the field and its write convention (relative to the store directory, written at index and refresh) are unchanged; an ordinary index or refresh after a move may update the stored relative value exactly as it does today.
