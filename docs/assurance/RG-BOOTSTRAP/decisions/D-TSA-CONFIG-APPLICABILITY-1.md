# D-TSA-CONFIG-APPLICABILITY-1 — a `paths` binding is static only where membership shows which tsconfig projects compile the file

Raised: 2026-10-03 by the document review of TS-ALIAS-RESOLUTION-1 INPUT-3 (cycle 2; reviewer codex gpt-6-sol; F-TSA3-01).

**The problem in plain words.** The packet let the nearest `tsconfig.json` win whenever it carried `paths`, and read `references` only when it did not. OBSERVED on amodx: `admin/tsconfig.json` has `files: []`, two `references` and `"@/*": ["./src/*"]`; it compiles no file itself — `admin/tsconfig.app.json` (66 files per the TypeScript API) does. The two mappings agree, so the predicted 416 bindings are the compiler's; but the rule would also emit a STATIC edge from a root config's mapping for a file compiled only by a referenced project whose mapping differs, and D-TSA-RECORD-CONFLICT-1 makes static assert the compiler's binding. The packet also called membership approximate while omitting `allowJs` and `outDir`.

**Options (reward / risk, by usefulness to an agent net of misdirection).**
- A — applicability by MEMBERSHIP, always: the nearest `tsconfig.json` (after its `extends` chain) and each of its `references` (one level, relative paths) is a candidate project; a project COVERS the file when its `files` lists it, or its `include` (default: everything under its directory when neither `files` nor `include` is set; nothing when `files` is set without `include`) matches it and its `exclude` (default `node_modules`, `bower_components`, `jspm_packages`) does not, a `.js/.jsx/.mjs/.cjs` file counting only when that project has `allowJs: true`, and a file under the project's `outDir` never; the file's aliases come from the covering projects — the distinct effective mappings (anchor directory, `baseUrl`, `paths`) of ALL covering projects feed the alias stage (D-TSA-CONFLICT-EVIDENCE-1 says how several are combined); NO covering project → the stage has no aliases for the file and declines (the row stays as at HEAD, the workspace stage runs as at HEAD). Reward: a static edge exists only where a project the reader can name compiles the file under that mapping; amodx and hexmanos bind through their `tsconfig.app.json` (membership `include: ["src"]`), the renderer through its own `include` globs. Risk: a file compiled by a project the one-level reader cannot see (a referenced project's own `references`, a package `extends`) gets no alias binding — a decline the agent sees as HEAD's unresolved project-alias row, never a wrong edge.
- B — keep "nearest with `paths` wins". Reward: fewer reads. Risk: a static edge the compiler does not make, exactly the fabrication class the certainty rule exists to prevent.
- C — bind INFERRED when the governing project is undetermined. Risk: INFERRED is reserved for what the index cannot determine (RG-REQ-002-L11); here the index CAN determine it by membership, so the mark would hide a readable fact.

Resolved: 2026-10-03 by the OPERATOR (in-place manager) as **A**, overridable by the human. Tests bound: a root config with `files: []`, `references` and its own differing `paths` binds through the referenced project's mapping, not the root's (counterexample with different indexed root and child targets); `allowJs` membership for a `.js` file; a file under `outDir` is not a member. The predicted movement (amodx 416, hexmanos 95, storybook 1) is restated by the author's simulation under this rule before the packet is re-emitted, or the difference is reported.
