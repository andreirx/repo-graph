# D-MDSS-SCOPE-1 — under a module filter, `modules deps` prints that module's own counts and names the universe in the block header; without a filter the block is byte-identical to today

Raised: 2026-10-04 by the manager packeting round-eight queue item 6 (RC-3, `docs/audits/2026-10-03-root-causes-v0.20.0.md`).

**The problem in plain words.** `rmap modules deps <module>` prints `Module: <X>` and then a `Summary:` block whose three numbers are the REPO-WIDE derivation diagnostics. VERIFIED live 2026-10-04 on isolated copies of the retained v0.20.0 stores: leveldb `modules deps table` prints `185 cross-module dependencies · 140 intra-module imports · 18 imports from unowned sources` while `table`'s four rendered edges sum to 46 imports; poco `modules deps Foundation` prints 2006 while Foundation's 24 edges sum to 1653. Cause: the counters are incremented once, repo-wide, in `classification/src/module_edges.rs:220-262` and returned as `facts.diagnostics`; `handle_modules_deps` (`daemon-runtime/src/dispatch.rs`) filters the EDGES by module and direction but copies `facts.diagnostics.*` unfiltered into the answer (`:8517-8523`), and the renderer prints them under the module line (`rgr/src/presentation/modules_deps.rs:138-151`). Never worked: the Summary predates the module filter. Intra-module and unowned imports are dropped during derivation (`continue` at `:232/:241/:251`), so the handler cannot recount them from the edges. Requirement: RG-REQ-002-L03 — every measured count states its universe.

**Options (reward / risk, by usefulness to an agent net of misdirection).**
- A — count per module inside the one derivation (RG-REQ-004-L01: trust and modules read one module-edge computation): the diagnostics gain, beside the unchanged repo-wide counters, per-module counters keyed by canonical path — intra-module imports of X (source and target owned by X), unowned-source imports INTO X (target X, source unowned), unowned-target imports FROM X (source X, target unowned) — over the imports the view admits; under a module filter the handler emits X's counters, with the cross-module figure the sum of the filtered edges' `import_count` (direction applied: outbound = X's outbound edges, inbound = X's inbound, all = both), and a `diagnostics_scope: "module"` key; without a filter the handler emits today's repo-wide counters and `diagnostics_scope: "repo"`. Human: under a module the block header states its universe — `Summary (module <X>, <direction label>):` with the module's figures, so the agent reads `46 cross-module dependencies` beside the four edges that sum to 46; without a module the block is `Summary:` with today's figures, byte-identical. Reward: the number under `Module: X` is X's number; the universe is stated where the figure is read; the repo-wide answer and `trust`'s reading of the same derivation are untouched. Risk: one additive map on the derivation diagnostics (per-module counters), one additive JSON key, one header form; no re-index (query time only).
- B — keep the repo-wide figures and label the block `Summary (repo-wide):` under a module. Reward: one line. Risk: the agent asking about X is told the repository's total and must know to ignore it; the right number remains unavailable.
- C — omit the block under a module filter. Risk: the agent loses the intra-module and unowned facts for X that only this surface could give.

Resolved: 2026-10-04 by the OPERATOR (in-place manager) as **A** — the fix at the cause RC-3 names; overridable by the human. The unscoped block stays byte-identical: its universe is the whole repository, stated by the absence of a `Module:` line and by `Queried:`; the human may rule the explicit `Summary (repo-wide):` label instead.
