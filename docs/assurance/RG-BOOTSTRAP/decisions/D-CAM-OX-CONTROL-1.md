# D-CAM-OX-CONTROL-1 — The macro-recovery marking fired on three non-macro forms in OpenXcom's yaml-cpp

Raised: 2026-09-26 by the implementation review of CPP-ATTRIBUTE-MACRO-1A (admission under INPUT-2, cycle 0; reviewer codex gpt-6-sol; finding F-CAM-R1, decision D-CAM-OX-CONTROL-1). CAM-A04's control corpus (OpenXcom, required byte-identical by P-CAM-01) changed in three nodes: `yaml-cpp/exceptions.h:204-207` `KeyNotFound(const Mark& mark_, const T& key_) : RepresentationException(mark_, …)` and the analogous `BadSubscript` constructor at `:261` were marked with candidates `[KeyNotFound, RepresentationException]` / `[BadSubscript, RepresentationException]`, and `node/convert.h:245` `YAML_CPP_API static bool decode(…)` with `[bool, decode]`. None is a trailing attribute macro; `bool` cannot be a member name.
Resolved: 2026-09-26 by the OPERATOR — option B (narrow the rule), under the human's ruling of the same day that ambiguity in our heuristics is the operator's to settle as the easiest honest rule (D-TEST-UNDETERMINED-1's standing rule). The human may override.

## Options (the reviewer's)
- **A** — ratify the broad shape-based marking and accept the three OpenXcom changes. Reward: the implementation stands. Risk: a false candidate (`bool`) and a false reason (`macro_recovery_ambiguous_identity`) on non-macro syntax — a wrong fact, not an ambiguity; contradicts RG-REQ-002-L11's "never guessed".
- **B (ratified)** — narrow the marking by two parse-tree facts, never by a name: the marker is recorded only when (1) the displaced candidate is a name node (`identifier`, `field_identifier` or `destructor_name` — leveldb `util/mutexlock.h:28` `~MutexLock() UNLOCK_FUNCTION() { this->mu_->Unlock(); }` stays marked), never a type keyword (`primitive_type`, `sized_type_specifier`) or a storage/function specifier, and (2) no `:` token (a member-initializer list) lies between the displaced candidate and the declarator-slot identifier — as in `KeyNotFound(…) : RepresentationException(…)`; a `:` AFTER the declarator (leveldb `util/mutexlock.h` `explicit MutexLock(port::Mutex* mu) EXCLUSIVE_LOCK_FUNCTION(mu) : mu_(mu) {`) does not suppress the marker. Every other shape keeps today's node unmarked, exactly as before this slice. Reward: leveldb's result is kept (its trailing macros satisfy both facts); OpenXcom returns to byte-identical (P-CAM-01 as approved); no name convention enters (the human's Q2 ruling: shape-based). Risk: a trailing-macro member whose recovery displaces a non-identifier stays unmarked (as today); whether any leveldb member is affected is decided by CAM-A04's unchanged leveldb oracle (35 → 15 marked, the listed pairs), not asserted here.
- **C** — defer. Risk: leveldb's 20 phantom fields and unmarked identities remain.

## Resolution
B. Allocation (→ INPUT-3): §2.1 rule 2 gains the two conditions; CAM-A01 names three regression tests built from the observed lines — `constructor_with_member_initializer_list_is_not_marked` (yaml-cpp `KeyNotFound`), `leading_export_macro_before_a_primitive_return_type_is_not_marked` (yaml-cpp `bool decode`), `trailing_macro_followed_by_a_member_initializer_list_is_still_marked` (leveldb `MutexLock`); P-CAM-01's OpenXcom identity oracle is unchanged. Adjacent defect, not this slice: the two yaml-cpp constructors are stored under the initializer's base-class name (`RepresentationException`) today — follow-up CPP-CTOR-INITIALIZER-NAME-1.
