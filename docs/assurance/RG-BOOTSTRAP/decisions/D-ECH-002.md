# D-ECH-002 — The LiveGraph route and the verified cycle walk: what the two engines mean, and what EXPLAIN-CYCLES-HONEST-1 does about the red parity certificate

Raised: 2026-09-19 by the in-place manager after the accepted EXPLAIN-CYCLES-HONEST-1 candidate (third admission, 13/13 obligations, 12/12 checks) failed the operator gate suite on two tests outside the allocation: `explain_serve_tests::m2_parity_explain_path_focus_equals_sqlite_with_nonempty_cycle` (rust/crates/daemon-runtime/src/explain_serve_tests/mod.rs:505) and `orient_serve::tests::m2_parity_full_serve_equals_sqlite_path_focus` (orient_serve/tests.rs:1462). Both assert that the M-2 LiveGraph decorator's path-focus serve is value-identical to the bare SQLite serve; the candidate made the SQLite focus reads carry `walk` (a verified ring) and `type_only`, while the LiveGraph route still emits neither.
Resolved: 2026-09-19 by the HUMAN ("Second direction for now, first as tech debt/later roadmap item, proceed with Q4, file the record fixes").

## Problem (plain language)

repo-graph has two engines that can answer "which modules sit on an import ring, and through which edges". The SQLite store is witness P — every import statement the extractors saw, bound to a file by repo-graph's OWN resolution stages (relative path + extension map, C/C++ include roots, Rust crate roots, Java path-suffix; `indexer/src/resolver.rs:427-640`), all languages, no compiler; what does not bind is preserved in `unresolved_edges` with a named basis. The in-memory LiveGraph is witness S — fed only by a scip-typescript index (`daemon-runtime/src/livegraph_refresh.rs:288-361`; dev-only `rmap dev livegraph-refresh`); its CALLS/References are compiler-verified, but its IMPORT edges are the ts-extractor's AST declarations resolved against the resident file inventory plus, in memory only, tsconfig `paths` aliases and literal dynamic imports (`repo-graph-livegraph/src/lib.rs:1232-1344`). On a non-TypeScript repo S is empty and every route serves P.

So the "resolved after compiling and linking" vs "resolved from code" split exists today only for calls (M-R2's ratified P ∪ S union with per-edge witness provenance, `docs/slices/recon-design-1.md:665-684`, flag-gated behind S-1..S-3). For imports and cycles both witnesses are from-code resolvers with different rule sets; the ratified rulings treat S as a CACHE of P for cycles (certified on cycle member sets only — `module_cycle_compare.rs:32-56`; walk, type_only and edges explicitly excluded, `livegraph_feed.rs:2340-2400`), and any divergence serves P labelled `LiveGraphCycleDivergence`.

What the three cases mean: (1) both report the same ring — resolver-independent at that fingerprint, the strongest claim repo-graph can make (still not "all cycles": neither witness sees package-external or re-export imports). (2) P reports a ring S lacks — almost always because the partition is not TypeScript or not resident (S never looked); otherwise an edge bound by a P-only stage. (3) S reports a ring P lacks — a REAL product gap in P: P has no tsconfig-alias stage, so `FRAKTAG/packages/ui/src/App.tsx:1` `import KnowledgeTree from "@/pages/KnowledgeTree";`, `components/ui/separator.tsx:4` `import { cn } from "@/lib/utils"` (20 files under the `@/*` alias of `packages/ui/tsconfig.json:9-11`) and `amodx/renderer/src/app/[siteId]/layout.tsx:1-3` (`@/components/Providers`, `@/lib/dynamo`) land in `unresolved_edges` as `SpecifierMatchesProjectAlias` (`classification/src/unresolved_classifier.rs:130-132`) and contribute no module edge — a ring through `@/lib/utils` is invisible to `cycles`, `modules`, `trust` and `explain` on every route, and S's knowledge of it is discarded by the cert.

The immediate defect: the candidate's verified walk is a per-edge fact of witness P; S cannot compute it (its module edge set is not certified equal to P's — `livegraph_feed.rs:2517-2524`), so the M-2 decorator on a TypeScript repo with a resident LiveGraph and a green cert would REPLACE the focus-cycles value with an unordered one (`explain_coherence.rs:205-211` swaps unconditionally; the divergence fallback fires only on an empty live filter) — the same repo answering differently by daemon warmth, and Q4's ring dormant on that route. The manager's packet said "the LiveGraph serve is unchanged" without listing the parity certificate in the regression watch, and the acceptance boundary did not include `daemon-runtime --lib`; that is the manager's oracle defect.

## Options put to the human

- Direction 1 — move imports/cycles to the M-R2 model: P ∪ S per edge with witness provenance, divergence surfaced (revive CYCLE-FACTS-2 part (a) edge-set certification; eventually a compiler witness for imports). Reward: the long-horizon shape of "the two engines answer different questions". Risk: a spec-sized change across the cert, the feed and every cycles surface; not a patch.
- Direction 2 — keep S as a cache of P for cycles; treat the alias gap as a P resolver defect (a tsconfig-alias resolution stage in the SQLite indexer, RG-REQ-006-L04) so P sees `@/lib/utils` on every route. Reward: smallest product-visible step, consistent with every ratified ruling. Risk: S's alias knowledge stays unused until the P stage ships.
- For Q4 now, under either direction: the LiveGraph serves the focus-cycles leaf only when it can reproduce the whole value; it cannot carry the walk, so the focus reads delegate to SQLite (labelled), the parity tests assert that, the ring renders on every route, nothing fabricated. Alternatives rejected: computing the walk on the LiveGraph route (byte parity not certifiable — ring choice depends on the edge set, CYCLES-WALK-DETERMINISM-1); relaxing the certificate to ignore `walk`/`type_only` (ratifies route-dependent output; its only reward is cost); holding Q4 (RC-4 stays live on every route).
