# D-JSAH-CURSOR-1 — the constructor cursors `explain <Type>` prints are stable keys, on every language

Raised: 2026-10-05 by the operator while root-causing JAVA-SYMBOL-AMBIGUITY-HINT-1.

**The problem in plain words.** When a bare name resolves to a type over its constructors, `explain` prints `N constructor(s) also match: explain '<cursor>'` so the constructor query is never hidden (CPP-DECLARATORS-1 §2.3). Today the cursor is the constructor's QUALIFIED NAME (`explain 'Widget::Widget'`; test `render_constructor_counted_line_reports_omitted_total` pins `3 constructors also match: explain 'Widget::Widget'`). A class with more than one constructor has several constructors with that same qualified name, so the printed cursor is itself ambiguous — it does not run as printed (RG-REQ-012-L03). For Java the qualified name would be `<pkg>.<Type>.<init>`, shared by all constructors of the type (kafka `KafkaProducer`: six).

**Options (reward / risk).**
- A — the cursor is the constructor's stable key (the full key `find` prints: `<repo_uid>:<path>#<name>:SYMBOL:CONSTRUCTOR[:dupN]`), on C++ and Java alike; one cursor per constructor, each runnable. Reward: every printed cursor runs (L03); one cursor form across `find`, the ambiguity listing and this line. Risk: longer lines; the C++ render tests' expected strings change (renamed in the packet).
- B — the qualified name when the type has exactly one constructor, the stable key otherwise. Reward: short cursor in the common case. Risk: two cursor forms for one line; the reader must know which one they got.
- C — keep the qualified name. Risk: an unrunnable cursor whenever a class has several constructors (L03 violated today on C++).

**Resolved: 2026-10-05 by the OPERATOR (in-place manager) as A**; the human may override.

**Correction 1 (2026-10-05, operator; JAVA-SYMBOL-AMBIGUITY-HINT-1-PREP cycle 3, the reviewer's JSAH-CONSTRUCTOR-QUOTE decision — option A, implied by RG-REQ-012-L03 and this record's rule that every printed constructor cursor runs as printed).** The slice had kept `render_related_cursors` (`rust/crates/rgr/src/presentation/explain.rs:316-333`) unchanged; that code inserts the target between literal single quotes, so a stable key whose path contains an apostrophe would print a cursor that does not run. The constructor line therefore quotes each key with `presentation::shell_quote_arg` (the same encoder as the ambiguity listing and `find`); for every key without an apostrophe the bytes are the same `'<key>'`, and a key with an apostrophe renders as `'…'\''…'`. One more test (`render_constructor_cursor_with_apostrophe_is_shell_quoted`). No measured key in the retained stores carries an apostrophe — this is the rule's completeness, not a reproduced corpus failure. Option B (limit the claim to measured keys) would have needed a human amendment of RG-REQ-012-L03 and is declined; the human may override.

**Correction 2 (2026-10-05, operator; JAVA-SYMBOL-AMBIGUITY-HINT-1-PREP cycle 4, the reviewer's finding against Correction 1).** Correction 1's sentence "No measured key in the retained stores carries an apostrophe" is false as written and is corrected (not rewritten): across the 29 retained v0.20.0 stores (latest snapshot each, read-only immutable queries by the operator), 1204 SYMBOL stable keys contain an apostrophe — Rust lifetimes and generics in qualified names, e.g. codegraph 566 repo_01m3zpxdt3t414ggjhq48r0cc5:__tests__/fixtures/kernel-parity/torture.rs#Parents<'a>.next:SYMBOL:METHOD — while 0 CONSTRUCTOR keys do. So the apostrophe case is REAL for the ambiguity listing (`callers`/`callees`/`path` over such symbols) and hypothetical only for the constructor line; both renderers quote with `shell_quote_arg`, and the slice's apostrophe tests use a Rust-shaped key. Evidence: agent-manager scratchpad `jsah1/apostrophe-measure.txt`.
