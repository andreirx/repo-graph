# D-JSAH-READ-STATE-1 — an ambiguity candidate whose store row is missing and one whose store read failed are two different states, each named in the payload and in the human listing

Raised: 2026-10-05 by the implementation reviewer of JAVA-SYMBOL-AMBIGUITY-HINT-1 (admission 1, cycle 1; the reviewer's label JSAH-CANDIDATE-READ-STATE).

**The problem in plain words.** The accepted allocation said: a candidate key whose row is missing is listed with its key and nulls. It said nothing about a FAILED store read. The candidate therefore folds `Err(e)` from `symbol_row_by_stable_key` into the same null-field object as `Ok(None)` (`dispatch_ambiguous_matches.rs`, the `outcome =>` arm), logging the error only on the daemon's stderr. A socket client sees the same listing and cursor for "the store has no such row" and "the store could not be read", and the human line `a stable key names exactly one symbol` is printed under a row that may be either. This breaks RG-REQ-002-L04 (a failed read renders unknown-with-reason, enforced in code) and the project's domain rule that not-found and lookup-failed are distinct outcomes (`Result<Option, E>` exists for exactly this). All four ambiguity sites share the builder.

**Options (reward / risk).**
- A — fail closed: a missing row or a failed read turns the whole answer into a runtime error. Reward: no misleading cursor. Risk: the other candidates are lost for one bad key; the resolver's honest listing disappears.
- B — keep every candidate and mark the state per candidate: the payload carries `lookup`: `{"kind":"found"}` | `{"kind":"missing"}` | `{"kind":"read-failed","reason":"<error text>"}`; the human row for a non-found candidate reads `  <n>. ? — no stored row for this key (its cursor will answer symbol not found)` or `  <n>. ? — store read failed: <reason>`, followed by the cursor as today; found rows and the hint are unchanged. Reward: nothing is lost, and the reader knows which fact is unknown and why. Risk: one more payload field and two more row forms; two more tests; a document amendment (INPUT-2) and a re-admission.
- C — defer acceptance. Risk: the failure path stays indistinguishable.

**Resolved: 2026-10-05 by the OPERATOR (in-place manager) as B** — implied by RG-REQ-002-L04 and the ratified domain rule; the human may override. The slice document carries the three states in its seam, §2.2 and §2.3 (INPUT-2); the two new tests prove them with an in-memory store that has the row, lacks the row, and cannot be read (a dropped `nodes` table). Known limit stated in the record: the found-row path and the hint text are unchanged, so no byte-identity witness moves.
