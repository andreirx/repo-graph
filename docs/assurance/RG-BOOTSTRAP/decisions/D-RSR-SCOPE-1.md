# D-RSR-SCOPE-1 — one slice binds every intra-crate Rust `use` form through one module-path ladder in the resolver; the field proof runs on three Rust corpora

Raised: 2026-10-04 by the manager packeting RUST-SELF-RESOLUTION-1 (RC-13, `docs/audits/2026-10-03-root-causes-v0.20.0.md`), after the human's ruling "rust self resolution slice … eating our own dog food was on the menu and we forgot about it".

**The problem in plain words.** On its own repository rmap binds no import that stays inside a crate. MEASURED on an isolated copy of the v0.20.0 self store (`401063a802312008.db`, `immutable=1`): of 5,152 unresolved imports, 3,204 are Rust `use` statements that name a module of the same crate, in three written forms: (1) a RELATIVE HEAD with a path — `use crate::dto::signal::X`, `use super::support::Y`, `use self::a::Z` (2,092 rows; the extractor writes a FILE key `<repo>:src/dto/signal:FILE` that lacks the crate directory and the `.rs`/`mod.rs` suffix, so stage 1 never finds it and the resolver's own comment says these rows "already resolve"); (2) a BARE HEAD — `use super::Y`, `use crate::X` (217 rows; the specifier is the word `super` or `crate` alone, which the extractor's `starts_with("super::")` test does not recognise as relative, so the row falls to the crate-internal heuristic); (3) a SIBLING PATH — `use context::open_storage` inside `cli/mod.rs` when `context` is a module declared in that file (900 rows, Rust 2018 uniform paths; the resolver tries only declared crate names). `rmap imports rust/crates/agent/src/aggregators/trust.rs` prints `0 imports` and ten rows "without a confirmed target", every one of them a file of the same crate. The same holds on every Rust repository in the corpus (vscode `cli/` 702 rows, codegraph 303, zap-engine 284).

**Options (reward / risk, by usefulness to an agent net of misdirection).**
- A — one slice, one ladder: the extractor records the specifier as the target key for every `use` (as it already does for `use other_crate::…` and as the TS extractor does for a bare specifier); the resolver's Rust stage gains ONE arm that turns the source file's path into its module path and probes `<crate_root>/src/<segments>.rs` → `<segments>/mod.rs` → shorten → `lib.rs`/`main.rs` — the SAME ladder RG-REQ-006-L01 ratified for `use <crate>::…`, factored into one function with two callers. Form (3) enters the arm only after the declared-crate stage misses, so every binding the store holds today is kept. Reward: on repo-graph 3,174 of the 3,204 rows bind (replay of the ladder over the store's file list, `predict.py`); `imports`, `explain` and `modules deps` answer the question "what does this file use inside its crate". Risk: a sibling name that is NOT a module file (an inline `mod x { }`, a `use`-re-exported module) climbs the ladder to the parent file or the crate entry — the parent file is where the inline module is written, so the binding is the defining file; a `#[path = "…"]` module stays unparsed (as L01 already states for `[lib] path`).
- B — three slices (relative heads; bare heads; sibling paths). Reward: smaller diffs per review. Risk: the same resolver function, the same extractor site, the same oracle and the same contract subsection are re-opened three times, with a bootstrap re-pin each time (TD-030); nothing an agent sees is better in between.
- C — relative heads only (form 1). Reward: the largest class. Risk: `imports` on the same file prints resolved rows beside a `super  line 18  this repository?` row that the index could have bound; the bare-head extractor defect (`is_relative` false) keeps mis-classifying call receivers imported through `use super::X`.

Resolved: 2026-10-04 by the OPERATOR (in-place manager) as **A**; the human may override. Field corpora: repo-graph (pinned worktree at the launch HEAD), zap-engine, codegraph — three Rust shapes (a Cargo workspace of 60 crates; a workspace with `examples/*` crates; a single crate in a subdirectory). vscode's `cli/` crate is a prediction only (the full TS repository costs two indexes of 9,000+ files for a shape codegraph already covers); hexmanos (TS + Java) is the non-Rust byte-identity witness.

## What this record rules
- The extractor's `target_key` for every Rust `use` is the specifier; `is_relative` is true for a head that is `crate`, `super` or `self`, bare or followed by `::`; `rust_module_to_path` is removed (no caller remains).
- Resolver order for a Rust IMPORTS edge: stages 1–3 unchanged → stage 3.5 (declared crate name, unchanged) → NEW stage 3.6 (module path against the source file) → stage 4 unchanged. A non-Rust edge never enters 3.6 (the existing `is_rust_import` gate).
- Stage 3.6's source anchor: the longest declared Cargo root that is a path prefix of the source file (the existing `rust_crate_roots` values); a source outside `<root>/src/` or under `src/bin/` binds nothing; the module path of `src/a/b.rs` is `a::b`, of `src/a/mod.rs` is `a`, of `src/lib.rs`/`src/main.rs` is the crate root; `super` pops one segment per occurrence and binds nothing above the root.
- The classifier's `parse_import_specifier` recognises the bare heads too, and the `imports` basis phrase restates that predicate (D-AGENT-USEFULNESS-FRAME-1).
- The extractor version `rust-core:0.2.0` → `0.3.0` and `INDEXER_VERSION` bump (RG-REQ-001-L06: a changed extractor is a toolchain change the staleness surface names).
