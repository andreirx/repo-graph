# D-DFSR-SCOPE-1 — `doctor` names the probed transport and state root first; its daemon probes are scoped to that root; a forced stdio transport makes the socket probes `n/a`, not failures

Raised: 2026-10-05 by the manager packeting round-eight queue item 10 (RC-4, `docs/audits/2026-10-03-root-causes-v0.20.0.md`).

**The problem in plain words (VERIFIED 2026-10-05 on the HEAD release binary 0.20.0 / 381cbb1f).** With `RMAP_STATE_ROOT`/`RMAP_SOCKET_PATH` set and `RMAP_TRANSPORT=stdio` — the configuration every sandboxed builder and every isolated proof runs under (RG-REQ-011-L06, L08) — `rmap doctor` prints `[ok] daemon_service: running (pid: 32224)` (the operator's launchd daemon on the GLOBAL root, `platform/macos.rs:207-225` reads `launchctl print gui/<uid>/<label>` and never looks at the probed root), `[FAIL] daemon_socket: socket not found: <iso>/rmap.sock` plus `[FAIL] socket_file / socket_connect / socket_ping: skipped (socket missing)`, and NO `transport` or `state_root` line, because `granular_socket_probes` (`platform/mod.rs:173-250`) returns before probes 4 and 5 whenever the socket is missing or unreachable. Verdict `daemon UNHEALTHY (5/25 checks failed)`, exit 1 — while every daemon-backed probe (`authority_policy`, `activity`, `retention`, enrichment, storage, resources) answered through the stdio daemon. In the normal environment the same binary prints `transport: auto (active: socket)` and `state_root: global` and `daemon healthy (25 ok · 1 note)`. So an agent in a sandbox is told the wrong daemon is running, that the daemon it is actually using may have crashed, and never where its state lives — one snapshot, two stories (RG-REQ-002-L02; RG-REQ-002-L08: labels describe the reader's subject).

**Options (reward / risk).**
- A — three bounded changes in the `doctor` seam: (1) emit `transport` and `state_root` FIRST, computed from the client configuration (`TransportMode::from_env()`, `StateRootMode`, the override path) without connecting; (2) when the transport is forced stdio (`RMAP_TRANSPORT=stdio`), the socket probes (`daemon_socket`, `socket_file`, `socket_connect`, `socket_ping`) report `n/a (stdio transport)` and pass; under `auto`/`socket` they keep today's failure semantics (a missing override socket IS a failure); (3) `daemon_service` is labelled by what it measures — `launchd service (global state root)` — and, when the probed root is an override or sandbox root, carries the detail `not the daemon serving this state root`. Reward: an agent under isolation reads where its state lives, which transport serves it, and no false crash diagnosis; the verdict follows the probes that matter. Risk: the health verdict changes in the stdio case (UNHEALTHY → healthy when the stdio daemon answers); the JSON probe list gains two early entries and reorders — `doctor --json` consumers that index by position would move (none known; the contract names probes by `name`).
- B — only emit `transport`/`state_root` early; keep the socket failures and the launchd line as they are. Reward: smallest diff. Risk: the false `UNHEALTHY` and the wrong-daemon line stay — RC-4's user-visible misdirection is not removed.
- C — scope `daemon_service` to the probed root by reading a pidfile under the state root. Reward: a true per-root service answer. Risk: no pidfile exists today; a new daemon-side artefact — a wider slice than RC-4 names.

**Resolved: 2026-10-05 by the OPERATOR (in-place manager) as A**, overridable by the human. Written as RG-REQ-011-L12 (PROPOSED); implemented by DOCTOR-FALLBACK-STATE-ROOT-1.

**Correction 1 (2026-10-05, operator; bootstrap re-pin review of RG-REQ-011-L12, passes 1–3).** Option A stands in substance — the `doctor` seam, no pidfile, no per-root service detection — with its three changes restated as RG-REQ-011-L12 revision 4 now binds them: (1) `transport: stdio (configured)` and `state_root` print first ONLY under forced stdio (`RMAP_TRANSPORT=stdio`), where both are determined before any connection; under `auto`/`socket` the two probes keep today's position (the active transport and a sandbox-local root are only known after the connection attempt); (2) under forced stdio FIVE socket-related probes are `n/a (stdio transport)` passes — `daemon_socket`, `socket_file`, `socket_connect`, `socket_ping` and `socket_path`; (3) the launchd/systemd service probe is a passing note with the detail `not the daemon serving this run` WHENEVER the client does not use that service — forced stdio (also on the global root, where the client spawns a subprocess daemon) or an override/sandbox state root — and a counted pass/fail only under `auto`/`socket` on the global root; the label names what it measures (`launchd service (global state root)`; on Linux the service mode in use, `systemd service` or `manual pid file`, both in DFSR-LINUX-1). The verdict logic is unchanged (it counts `passed`). The operator approves this revised scope; the human may override.

**Correction 2 (2026-10-05, operator; DOCTOR-FALLBACK-STATE-ROOT-1 document review cycle 1, decision DFSR-D01 resolved A — the reviewer's recommendation).** The service note must not assert which daemon answered when that is unproven. `StateRootMode::Override` follows `RMAP_STATE_ROOT` alone while socket selection follows `RMAP_SOCKET_PATH` alone (`daemon_client/mod.rs:154`, `platform-paths/src/socket.rs:99`): with only `RMAP_STATE_ROOT` set under `auto`, the client can reach the GLOBAL launchd socket, so `not the daemon serving this run` would be false there. Resolution: under forced stdio the note states the known fact — `the client runs its own stdio daemon; this service did not serve this run`; under a configured non-global state root with `auto`/`socket` transport the note is neutral — `measures the global launchd service; this run's configured state root is <path>`. Options declined: B (verify the responding daemon's identity — a new mechanism beyond RC-4), C (omit the probe — loses the observation), D (keep the sentence — a known counter-case misleads). RG-REQ-011-L12 revision 6 binds the two details.
