# D-REFRESH-STALE-1 — When an extractor's rules change, how does an existing store learn about it?

Raised: 2026-09-23 by the first document review of CPP-ATTRIBUTE-MACRO-1A (codex gpt-5.6-terra, D-CAM-REFRESH-1): except when a changed-config widening re-extracts its scope (`indexer/src/invalidation.rs Disposition::ConfigWidened`), delta refresh copies forward files whose content hashes match (`indexer/src/orchestrator.rs copy_forward_unchanged_files`) and toolchain versions are not an invalidation input, so a semantic extractor or resolver change never reaches an existing store's unchanged files until a full reindex — a gap every earlier extractor and resolver slice carried unnoticed. Each snapshot records its toolchain (`toolchain_json`: `{"extractors":["ts-core:0.2.0","c-core:0.1.0","cpp-core:0.1.0",…],"indexer":"indexer:1.0.0"}`, orchestrator.rs:250/:1812 `build_toolchain_json`) but no current `orient` or `check` path compares it with the running toolchain or reports toolchain staleness (`daemon-runtime/src/util/trust.rs:44` only passes it through to the trust report).
Resolved: 2026-09-23 by the HUMAN — "B rebuild".

## Options
- **A** — version-keyed invalidation: when a language's extractor version differs from the snapshot's, refresh re-extracts every file of that language. Reward: refreshed stores become correct for every past and future change. Risk: a one-time whole-language re-extraction per upgrade; a new invalidation mechanism before the queue continues.
- **B (ratified)** — no invalidation; an explicit `rmap repo rebuild` is the remedy, and `check`/`orient` render a visible staleness line ("C++ facts from cpp-core:0.1.0 (current cpp-core:0.2.0) — run rmap repo rebuild <path> to refresh") whenever the running toolchain differs from the effective stamped-or-carried provenance of the facts served. Reward: no re-extraction cost; the degradation is stated where the agent reads it. Risk: stores stay stale until a human acts; a new fact must reach two surfaces. Responsibility split: the agent crate compares the running toolchain with the effective provenance of the facts served — the snapshot's `toolchain_json` including the provenance retained through copy-forward (D-REFRESH-STALE-2, option B: the `carried_forward` key) — as a pure function (inputs: the `toolchain_json` string, the running toolchain list, and the extractor-family names represented by files in the served snapshot; output: the three-state DTO); the indexer writes that provenance at refresh; the daemon supplies all three inputs at query time and attaches the result to orient (additive `value` field) and to check (`CheckInput` → the `TOOLCHAIN_STALENESS` condition); `rgr` renders the lines. A refresh's running-toolchain stamp alone is never evidence of `current`. dispatch.rs (over the CLAUDE.md size guardrail) gains only the two attach calls.
- **C** — leave refresh as is. Reward: nothing changes. Risk: a refreshed snapshot silently keeps facts the current binary would not produce — contradicts RG-REQ-001-L01 and RG-REQ-002-L11.

## Resolution
RG-REQ-001-L06 amended (RG-BOOTSTRAP-INPUT-9). Queue: TOOLCHAIN-STALENESS-1 ships BEFORE the re-cut extractor/resolver slices; each extractor slice bumps its affected extractor version constant (CPP-ATTRIBUTE-MACRO-1A: `cpp-core:0.1.0 → 0.2.0`) and each resolver/indexer slice bumps `INDEXER_VERSION` (`indexer/src/orchestrator.rs:59`; PYTHON-SUBMODULE-IMPORT-1 is one), so the line fires on every existing store, and states "existing stores need `rmap repo rebuild`" in its ship block.
