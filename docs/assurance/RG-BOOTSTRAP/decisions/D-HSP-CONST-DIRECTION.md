# D-HSP-CONST-DIRECTION — the shared usage constants live in `cli/usage.rs`; handlers import them through `crate::cli`; the `risk` command passes the coverage usage text to its renderer

Raised: 2026-10-04 by the requirements reviewer of HELP-SURFACE-PARITY-1-PREP (cycle 2, review; the author's report raised the same problem as D-HSP-CONST-VISIBILITY).

**The problem in plain words.** D-HSP-COVERAGE-CONST put the shared usage constants in the handlers (`commands/declare/*.rs`, `commands/quality/coverage_cmd.rs`). Two facts make that unimplementable as allocated. (1) Those modules are private (`commands/mod.rs:25,44`; `commands/declare/mod.rs:24,26,27`; `commands/quality/mod.rs:24`): a `pub(crate) const` inside them cannot be named from `cli/usage.rs` or `presentation/risk.rs` without re-exports in files outside the allocation (the author reproduced `error[E0603]: module 'quality' is private`). (2) Even with re-exports, `cli → commands` and `presentation → commands` would be new import directions: `cli/mod.rs:15-17` documents that command handlers, DTOs and family helpers live in `crate::commands` and use `cli` as infrastructure, and nothing in `cli/` or `presentation/` imports `crate::commands` today (OBSERVED, `grep -rn "crate::commands" src/cli src/presentation` empty). The direct imports would form two cycles: `commands → cli → commands` and `commands → presentation → commands`.

**Options (reward / risk).**
- A — define the four constants in `cli/usage.rs` (re-exported by `cli/mod.rs`); the handlers import them from `crate::cli` and print them unchanged; the `risk` command (`commands/quality/risk.rs`) passes the coverage usage text into the renderer (`presentation/risk.rs` receives it as a plain string — a DTO field or a render parameter — and never imports `commands` or `cli`). Reward: one source for the handler, the help and the hint; the documented directions (`commands → cli`, `commands → presentation`) are kept; no new module. Risk: revises D-HSP-COVERAGE-CONST's placement; two more candidate paths (`cli/mod.rs`, `commands/quality/risk.rs`); the renderer's call sites change; the handlers' printed bytes must stay identical (HSP-C03 step 5).
- B — keep handler-owned constants and pass them into the help and the renderer from the wiring in `main.rs`. Reward: placement unchanged. Risk: touches `main.rs`, which the slice freezes; wider visibility and wiring changes.
- C — re-export the constants and import `commands` from `cli` and `presentation`. Not acceptable: creates the two cycles; violates the documented direction.
- D — keep copied strings and test equality. Reward: no new dependency. Risk: reverses D-HSP-COVERAGE-CONST's no-copy rule; drift detected, not prevented.

**Resolved: 2026-10-04 by the OPERATOR (in-place manager) as A**, the reviewer's recommendation; the human may override. Basis: the dependency rule and the direction `cli/mod.rs` documents already imply it — no new edge, no new module; `cli` is the infrastructure layer the handlers consume. The candidate path set of HELP-SURFACE-PARITY-1 becomes nine: `cli/usage.rs`, `cli/mod.rs`, `commands/declare/{boundary,requirement,quality_policy}.rs`, `commands/quality/coverage_cmd.rs`, `commands/quality/risk.rs`, `presentation/risk.rs`, `docs/cli/rmap-contracts.md`. HSP-C02 asserts that no file under `cli/` or `presentation/` imports `crate::commands`.
