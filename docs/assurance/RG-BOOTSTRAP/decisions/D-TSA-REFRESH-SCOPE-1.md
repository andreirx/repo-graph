# D-TSA-REFRESH-SCOPE-1 — every `tsconfig*.json` / `jsconfig*.json` is a tracked config file, so a change to a referenced or extended project re-extracts the files it covers on refresh

Raised: 2026-10-03 by the implementation review of TS-ALIAS-RESOLUTION-1 admission 1 (reviewer codex gpt-6-sol; F-TSA-REFRESH and its decision D-TSA-REFRESH-SCOPE).

**The problem in plain words.** The alias stage reads `tsconfig.app.json` (hexmanos: the referenced project that supplies `"@/*"`), but the refresh planner knows config files by a literal filename table — `routing.rs` `is_config_file` and its mirror `invalidation.rs` `RECOGNIZED_CONFIGS` — that lists `tsconfig.json` and not `tsconfig.app.json`. A change to that file alone changes no tracked hash, so refresh copies every unchanged source file's old signal forward (`orchestrator.rs:1897`) and `frontend/src/App.tsx:2` can keep a static edge built from a mapping that no longer exists, in a snapshot reported current. HEAD has the same gap for a relative `extends` target (`tsconfig.base.json`): the alias reader followed it; the planner never tracked it. VERIFIED on the code: both tables are literal `matches!`/slice lists; a nested config's change widens to the unchanged files under its directory (`nested_config_widens_only_subdirectory`).

**Options (reward / risk, by usefulness to an agent net of misdirection).**
- A — recognise the file FAMILY: a filename matching `tsconfig*.json` or `jsconfig*.json` is a config file in both tables (the scanner already routes through `routing::is_config_file`); a change to a referenced or extended project then widens the refresh scope to the unchanged files under that config's directory, which are re-extracted under the current mapping. Two more candidate paths (`rust/crates/indexer/src/routing.rs`, `rust/crates/indexer/src/invalidation.rs`) and one refresh test with a changed `tsconfig.app.json`. Reward: the agent reads current alias edges after a refresh, by the existing widening mechanism; the HEAD `extends` gap closes for the common names. Risk: a config a project extends under another name (`shared/base.json`; a package `extends`) is still untracked — a stated limit, follow-up TS-CONFIG-REFRESH-1; a change to any `tsconfig*.json` re-extracts its subtree (the cost the mechanism already pays for `tsconfig.json`).
- B — a full index whenever any tsconfig changes. Reward: no dependency tracking to get wrong. Risk: refresh stops being a delta for the whole repository on a one-line config edit; a new behaviour class for the daemon's refresh contract.
- C — leave refresh as is and mark the snapshot stale. Risk: a stale-marked answer still shows the wrong edge; the human's ruling (2026-09-26) is that staleness is a rebuild/refresh signal and never a gate — so mark-and-serve is not a remedy.

Resolved: 2026-10-03 by the OPERATOR (in-place manager) as **A**, overridable by the human. The allocation grows to eighteen paths (D-TSA-SCOPE-1, correction appended). Tests bound: `routing` and `invalidation` unit tests for the family match and for the existing names (unchanged), a planner test that a changed nested `tsconfig.app.json` widens only its subdirectory, and the repo-index refresh test with a changed referenced config whose importer gains the new mapping's edge.
