# D-JSAH-SCOPE-1 — an ambiguous symbol lists runnable stable-key cursors; the hint never names a form the candidates share; a Java bare type name collapses to its type as C++ does

Raised: 2026-10-05 by the operator (in-place manager) while root-causing round-eight queue item 11 (JAVA-SYMBOL-AMBIGUITY-HINT-1; audit 2026-10-03 low observation; reproduced on the v0.20.0 kafka store with the HEAD release binary).

**The problem in plain words.** `rmap callers KafkaProducer.send` answers `symbol 'KafkaProducer.send' is ambiguous`, lists two rows and says `hint: use qualified name for exact match`. The two rows are the two overloads `send(record)` (`KafkaProducer.java:942`) and `send(record, callback)` (`:1061`); they have the SAME qualified name, so the hint cannot be followed — the fully qualified form gives the same error. The second row is printed as `KafkaProducer.send:SYMBOL  METHOD:dup2`: the daemon derives (qualified_name, kind) from the stable key with `rsplitn(3, ':')` (`daemon-runtime/src/dispatch.rs:228`), which mis-splits any key that carries the `:dupN` overload suffix, and it drops the stable key itself — the one identity that distinguishes the overloads and that `callers`/`explain` already accept (verified: `callers '<key>:dup2'` → exit 0, line 1061; `find --exact` prints exactly these keys as `→ rmap explain '<key>'`). Kafka alone has 3,345 overloaded METHOD and 1,101 CONSTRUCTOR nodes with a `:dupN` key, so every `callers <overloaded name>` hits this. Separately, `explain KafkaProducer` stays ambiguous against the class's six constructors, while `explain CGHeroInstance` on C++ resolves the class and lists "N constructors also match": the type/constructor collapse (`agent/src/explain/mod.rs classify_type_constructor_collision`) proves a constructor's membership with `rsplit_once("::")`, and a Java constructor's qualified name is `<pkg>.<Type>.<init>`. Both mechanisms never worked for this case (4fb521d8, 2026-05-19; 5c3ec2de, 2026-09-07, C++-only).
